I retested the original TypeVar reproducer on the current `master` branch. The local reference now resolves without the reported `py:class reference target not found` warning. This appears to have been fixed by #13808, released in Sphinx 9.0, which makes local Python-domain resolution fall back from `py:class` to `py:data` and `py:attr`.

The intersphinx cases mentioned in the comments remain unresolved. I reproduced the problem with an external inventory containing:

```text
py:data  foo.T
```

For an annotation targeting `foo.T`, `parse_reftarget()` creates a pending reference with `reftype="class"`. Local Python-domain resolution applies the fallback added in #13808, but intersphinx only searches the inventory object types associated with the `py:class` role. It therefore does not consider the `py:data` entry and leaves the reference unresolved.

I confirmed that the inventory entry itself was valid by repeating the lookup with the broader `py:obj` role, which successfully found `foo.T`. This isolates the problem to the mismatch between the `py:class` reference and the `py:data` inventory entry.

A potential fix would be to make intersphinx mirror the ordered fallback already used for local Python-domain references:

1. Search the normal `py:class` object types.
2. If no match is found, search `py:data`.
3. If there is still no match, search the object types associated with `py:attr`.

The original TypeVar reproducer can therefore be considered fixed in Sphinx 9.0 and later. I suggest keeping this issue open for the remaining intersphinx behavior and narrowing its title accordingly.
