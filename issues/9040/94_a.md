> As a just idea: Is it helpful to add a hook (or replace) configuration loading phase to implement this as an example extension?

I believe this is the best way forward for this issue: that is, for Sphinx to add a way for an extension to take responsibility for loading the configuration. That way, ExecutableBooks can write an extension that reads `sphinx.yaml`, @pradyunsg can write an extension that reads `sphinx.toml`, etc.

Obviously, there are questions to sort out (how does this extension get declared? what if multiple extensions take responsibility? what is the order of precedence? etc.), but I don't think a static configuration file is good for this project, discussed below.

I don't understand the problem. The `conf.py` file that is generated by running `sphinx-quickstart -p Project -a Author` and pressing Enter repeatedly is **valid TOML**. If you replace `=` with `:`, it is **valid YAML**.

A user does not need to learn Python or programming to edit `conf.py`. For a user to edit YAML or TOML files, they need to learn a few things like which values need to be quoted or bracketed, how variable names are separated from literal values, how to indicate lists and mappings, etc. The same effort is required to edit `conf.py` in simple ways.

If a user has no need for dynamic configuration, then there is really no difference between Python literals, TOML and YAML. Is changing the extension from `.py` to `.toml` or `.yaml` and using `:` instead of `=` of such great benefit that it is worth the downsides (below)?

It looks like most contributors to this issue (outside the Sphinx maintainers) are maintainers/users of Executable Books and maintainers of ReadTheDocs. While these are important projects, they are not the universe of Sphinx users. I would not rush to merge the PR without more discussion.

I think not enough attention is being given to the kinds of issues raised by @jakobandersen in https://github.com/sphinx-doc/sphinx/issues/9040#issuecomment-835461828 (discussed more below) and @tk0miya in https://github.com/sphinx-doc/sphinx/issues/9040#issuecomment-820500990 (similar to my comments above).


With respect to the various proposals:

* Non-coexistence of static and Python configuration files is a bad user experience, as @jakobandersen described in the linked comment. If the user at some later point in their journey needs a dynamic configuration, they need to either convert their static file to a Python file (how do they learn how to do this?) OR learn how to write an extension (!) that might require specific hooks that do not exist yet (!!!). This is not good if the goal is to help less technical users.
* Co-existence of two configuration files is not without problems. In the case of repeated variables, failing – as suggested by @pradyunsg – is better than clobbering, because it is almost never the user's intention to have a useless configuration in one file that always gets clobbered. But, there are other issues. 
  * In my experience, the least experienced users simply copy-paste snippets into the configuration file. This is unambiguously more complicated if there are two possible configuration files instead of one. Right now, all the existing tutorials, blog posts, StackOverflow answers, etc. offer instructions for what to paste into `conf.py`. A new file will generate new frustrations when people paste code into the wrong file. (With TOML, at least, there is a chance that the Python code still works. With YAML, there is no chance; it will either error or silently mis-parse the user's intent.)
  * Taking @tk0miya's example in https://github.com/sphinx-doc/sphinx/issues/9040#issuecomment-821329283, after the build errors, how will the user resolve it? Let's say they are a "copy-paste" user, who followed ExecutableBooks instructions to install one extension in `sphinx.yaml`, and followed StackOverflow instructions to install another extension in `conf.py`. Now they have two files with different syntaxes (and they might not know either - since they simply copy-pasted text), and they are expected to resolve the conflicts. They might stumble. They might not notice the error message (the most common issue that new command-line users face is learning which output is relevant and which is not), might not understand what they need to do, etc.
  * A user starts with a static file (let's say it's non-executable YAML). They want to add a dynamic configuration – something simple like setting `release = version`. If they try `release: version`, it will be interpreted as the string `"version"` (TOML will just error, which is more helpful). Maybe they learn to do `version: &version "1.0"` and `release: *version`. Now they want to do something like `copyright = f'2021, {author}'` in their `sphinx.yaml`, which they read in a tutorial intended for `conf.py`. Of course, we know that they can't. But from their perspective, why not? Why do they need to add this `conf.py` file (which they maybe never saw before), that can do the same things as the static file, but can also do string interpolation (etc.)? Why doesn't the static file support this feature? These are just simple examples, but in my experience, when there is a "nice" format with limited functionality and an "ugly" format with full functionality, the users always ask for the nice format to get more functionality. This is not a desirable situation for Sphinx maintainers.

One file in one syntax (i.e. no change) avoids these three types of user challenges that arise from co-existence, which I can summarize as:

* Syntax conflicts
* Configuration conflicts
* Non-substitutable formats

I can come up with more classes of user challenges that come with having two configuration files, but, really, I don't see what is wrong with `conf.py`, since in its basic form it is valid TOML and (after `sed 's/ = /: /' conf.py`) is valid YAML. If folks really want alternative formats, @tk0miya suggested an option (just as an idea) in the quoted text above.

FWIW, the comparison to `setup.py` and `setup.cfg` is not relevant, since it is generally *programmers* who write Python packages (and who are therefore capable of understanding the difference between the file formats, etc.), whereas this issue is intended to help *non-programmers*.
