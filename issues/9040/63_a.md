@tk0miya The other major benefit to using something that isn't executable is that it's parsable by computers, safely.

In RTD, you can see the outcomes of this:

* Mkdocs overriding theme (reading & overwriting the users YAML config): https://github.com/readthedocs/readthedocs.org/blob/924699cf0bea65ad8fa09f9f36cfb5dd7e832a7c/readthedocs/doc_builder/backends/mkdocs.py#L211-L214
* Sphinx overriding theme (with custom Python code _injected into the users conf.py_): https://github.com/readthedocs/readthedocs.org/blob/924699cf0bea65ad8fa09f9f36cfb5dd7e832a7c/readthedocs/doc_builder/templates/doc_builder/conf.py.tmpl#L52-L59

It's more complicated for us, and other people who want to read values from the config in any way (even in Python!)  To summarize:

* You can _read it much more safely_, since no code is being executed when users want to read values from the config files.
* There isn't any _python environment_ required for reading the config. This means CLI scripts and other languages can easily build tooling around it (eg. a version autoincrementer that runs from the CLI [we do this here](https://github.com/readthedocs/common/blob/f2c03fe69bcae705dcfe9dd0e79a9982691eba78/tasks.py#L67-L69) but can't easily do it for our python configs)
* We can also write a schema to validate YAML much easier than Python (an example for our [YAML schema here](https://github.com/readthedocs/readthedocs.org/blob/master/readthedocs/rtd_tests/fixtures/spec/v2/schema.yml#L1)).

Overall, having a configuration that isn't dynamically executed code is a major benefit to many users of Sphinx, especially people who are extending or building on top of the toolchain.
