### Describe the bug

I was using  epubcheck 4.2.6.2 to validate a sphinx-generated epub and got errors related to the identifiers being inconsistent between toc.ncx and content.opf.
I ended up digging through a bunch of the w3c specs and through the sphinx sources, and think that sphinx's toc.ncx template (and possibly the content.opf) template misunderstands the epub3 specification.
This issue is important because some of the professional ebook retailers will not accept a book with epubcheck errors and because the user has little opportunity for fixing without modifying the sphinx sources.
In particular, since the epub timples are rendered with copy_asset_file, you cannot simply override them like theme templates.
My analysis of the source is consistent with ecfd08d325 (recent master) and what's shipping in Debian bookworm.

## Desired Behavior
According to the [Epub 3.2 packages specification](https://www.w3.org/publishing/epub3/epub-packages.html#attrdef-package-unique-identifier), the unique-identifier attribute of the package element in content.opf is:

The unique-identifier attribute takes an IDREF [[XML](https://www.w3.org/publishing/epub3/epub-packages.html#bib-xml)] that identifies the [dc:identifier](https://www.w3.org/publishing/epub3/epub-packages.html#sec-opf-dcidentifier) element that provides the preferred, or primary, identifier. Refer to [Publication Identifiers](https://www.w3.org/publishing/epub3/epub-packages.html#sec-package-metadata-identifiers) for more information.```

```

In particular the *unique-identifier* is not the unique identifier itself, but rather points to a dc:identifier xml element.
It would be entirely reasonable for sphinx to set the id of the dc:identifier element it generates to "sphinx-id" all the time and to set the unique-identifier element in the package to "sphinx-id".


In contrast, the `dtb:uid` element in toc.ncx actually takes the unique identifier itself.
I cannot access the OPF 2.1 specification right now, which contains a pointer to the toc.ncx specification---I'm getting  network timed out accessing idpf.org.
I'm sure I'm right on this both from previous memories reading the spec,   and reading a lot of epub toc.ncx files.

## The Problem

Sphinx uses the same entry from the metadata dictionary both for the dtb:uid element and for the unique-identifier element.
Moreover the unique-identifier element needs to be an xml identifier---it needs to start with an alpha, not a number, so you cannot use a uuid for it.
B ut `dtb:uid` is typically a uuid, which will typically start with a number.
I mean I guess you could make things work by setting `epub_uid` to a uuid starting with a hex letter and then setting `epub_identifier` to the same string, but that's a massive hack, and ignores ISBNs and other identifiers.

## Source Dive

In the template context used to render epub templates:

* epub_uid is mapped to the uid key
* epub_identifier is mapped to id
* epub_scheme is mapped to scheme

The relevant part of the `templates/epub3/content.opf_t` template is:

```
<package xmlns="http://www.idpf.org/2007/opf" version="{{ epub_version }}" xml:\
lang="{{ lang }}"
 unique-identifier="{{ uid }}"
 prefix="ibooks: http://vocabulary.itunes.apple.com/rdf/ibooks/vocabulary-exten\
sions-1.0/">
```

Then later in the same file:

```
    {%- if epub_version == 3.1 %}                                               
    <dc:identifier id="{{ uid }}" opf:scheme="{{ scheme }}">{{ id }}</dc:identi\
fier>                                                                           
    {%- else %}                                                                 
    <dc:identifier id="{{ uid }}">{{ id }}</dc:identifier>                      
    {%- endif %}                                                                

```

But then the metadata from `templates/epub3/toc.ncx_t`:

```
    <meta name="dtb:uid" content="{{ uid }}"/>
```

## Fix

As mentioned in the title, changing `{uid}` to `{id}` in the `toc.ncx_t ` template should fix the problem.
I also think that the *epub_uid* variable should be removed and a constant identifier that will not clash with any *id* in the `content.opf` should be used.


### How to Reproduce

Build any epub.  In conf.py, set 

```
epub_identifier = #place a valid uuid here
epub_scheme = 'uuid'
```
And then run the resulting epub against epubcheck.  Or manually examine the toc.ncx and content.opf for conformance to the spec.
