# The problem

Typically, if you document the return type of a function using `:rtype:` field in Python, or if it is inferred by autodoc from the return annotation, then it shows up on a separate line, like this:

<img src="https://github.com/user-attachments/assets/c7274378-a4c9-4935-9fe2-07dfa37a25b7" width="350">

I find this pretty ugly, and it's inconsistent with parameter and exception types, which are on the same line as their description. I suspect it's only this way as a sort of historical accident. I think it ought to be on the same line as the return description, like this:

<img src="https://github.com/user-attachments/assets/c9f4a51d-453f-4af2-a730-b4ee3caaa497" width="350">

# Possible solution

As I noted in the discussion, there is a simple fix that produces that second output: change the `return` field [from `PyField`](https://github.com/sphinx-doc/sphinx/blob/eaebbec4d165efcb5048fc06431e3bf796c9d224/sphinx/domains/python/_object.py#L225) to type `PyGroupedField` (like `:exception:`). This is a backwards-compatible change, as far as I can tell, so it seems like it would be a small change that gives a useful feature with no downsides (except the cost to actually do it and document it).

```python
        PyField(  # change to PyGroupedField (and add can_collapse=True and remove has_arg)
            'returntype',
            label=_('Return type'),
            has_arg=False,
            names=('rtype',),
            bodyrolename='class',
        ),
```

# Bonus feature

Also noted in the above discussion, if implemented in the way I'm suggesting then you could list multiple return types/descriptions, like with exceptions, and they would get turned into a list. I've found this handy.

# Other points to consider

* The next logical step from this feature would be for autodoc to (optionally) transform return type annotations into this format rather than `:rtype:`-style. This is more complex than it looks because autodoc outputs type annotations by directly manipulating the docutils node tree after the fact.
* If agreed for Python, then it would presumably be worthwhile for other domains too (though I mainly care about Python, but I can imagine being interested in it for C++ one day).
* An alternative (or complementary) approach would be to make `:rtype:` directly support appearing on the same line as the description (under an option). This has the nice benefit that existing projects could switch to the layout with one change. But it would be harder to implement (I don't think any existing Python field types work that way) and doesn't have the bonus grouping feature.
