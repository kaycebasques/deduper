@picnixz I'm not very familiar with the autodoc code but tried to have a quick look at this. It does seem like the original class object is available in at least some situations – it's there in `self.object` of `ClassDocumenter`. In fact I found that I could just patch `ClassDocumenter.format_name()` (overriding the base class implementation `Documenter.format_name()`) to get the correct behaviour:

```python
    def format_name(self) -> str:
        """Format the name of *self.object*, with type parameters appended.
        """
        result = super().format_name()
        type_args = {}
        for p in getattr(self.object, "__type_params__", ()):
            type_args[p] = None
        for b in inspect.getorigbases(self.object) or ():
            if getattr(b, "__origin__", None) is typing.Generic:
                type_args.clear()
            for p in getattr(b, "__parameters__", ()):
                type_args[p] = None
        if type_args:
            prefixes = {"TypeVarTuple": "*", "ParamSpec": "**"}
            result += "[" + ", ".join(
                prefixes.get(type(a).__name__, "") + a.__name__ for a in type_args.keys()
            ) + "]"
        return result
```

I'm not saying this is the right place put it in the code (e.g., it should probably not be in a function called "format_name"), and there should probably be an option to `autoclass` to say whether to do this, ~~and I haven't included any code for supporting `*T` or `**T`~~ [Edit: I updated it for *T and **T] This is just meant to be a proof of concept that it's possible.

You talk about having the signature as a string. The only thing I could find like that in the code is if the signature is overridden by the user with a signature at the start of a docstring. For that, I think it's sensible to support PEP 695 type parameters (i.e. `class Foo[T](...)`, but that's a simple matter of the `ClassDocumenter` passing them unmodified to the output. The fancier work of the above function, converting parameters of base classes into PEP 695 type parameters, isn't relevant to that: if a user has explicitly said what the signature should look like, and (unlike when writing the actual Python code) they're not doing it that way because of old Python version compatibility, then it should be left alone anyway.
