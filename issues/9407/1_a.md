I'm using the `.. literalinclude` directive to include successive pieces of an example Python file in expository documentation. To do that without hard-coding line numbers, I'm making heavy use of marker comments, as in for example:

```python
# -- start setup
def example_of_setup():
    ...
# -- end setup

# -- start calculate
def example_calculation():
   ...
# -- end calculate
```

so that I can use `.. literalinclude` options like `:start-after: start setup`, `:end-before: end calculate`, and so on.

This works fine. But: when the code gets auto-formatted by the "black" utility, two blank lines are introduced before each end comment, and those two blank lines end up in the rendered output:

```python
# -- start setup
def example_of_setup():
    ...


# -- end setup
```

I'd like to be able to avoid those extra blank lines in the output without excluding the target file from `black` (which is what I'm currently doing), and without hard-coding line numbers in the `.rst` source.

Some possible solutions:

- a `:trim-blank-lines:` option that trims blank lines from the start and end of the included code block
- allow selecting all but the last two lines of a code snippet, perhaps with syntax like `:lines: -(-2)` or `:lines: -~2` or `:lines: --2`. (Note that extra blank lines at the *start* of a snippet can already be dealt with this way, by using `:lines: 2-`; it's just the ability to do this for extra blank lines at the end that we're missing.)

For reference, this is the project documentation where I'm experiencing this issue. I've highlighted one of the blocks that's shown in the docs using `.. literalinclude`. If there's a better way to do this, I'd love to hear about it. https://github.com/enthought/traits-futures/blob/973aa43787283d9e77d7ad840db008c30c1f73c4/docs/source/guide/examples/fizz_buzz_task.py#L30-L64
