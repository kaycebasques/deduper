Bumping this as I've been running into it myself. Following the PEP 695 support (#11561) being made available in Sphinx 9.0.0, this issue can be worked around by using `type Foo = NewType(Bar)` instead of just `Foo = NewType(Bar)`, which causes them to be considered as `:py:type:` by autosummary. However, this is a hacky workaround, as `type ... = NewType(...)` is **_invalid_** syntax wrt PEP 695 and PEP 484. 

Alternatively, [`:any:`](https://www.sphinx-doc.org/en/master/usage/referencing.html#role-any) works but this is a fragile and non-descriptive solution.

It would be very helpful for `NewType` to be handled properly by autosummary, as it's very useful for specifying certain derived classes which `type` and `TypeAlias` are currently unable to properly denote.

In my case, `NewType` is particularly useful in cases where the exact type implementation is not available, but it is known to derive from something else. In this situation, `NewType` can be used to enable meaningful type analysis where we might not otherwise have access to the explicit definition. E.g., I'm working with an externally-defined data structure (i.e., non-Python) called `Foo`, that is known to derive from and extend another data structure `Bar`. `NewType` can be used to indicate this relationship intuitively.
