**Is your feature request related to a problem? Please describe.**

[Scorer.score()](https://github.com/sphinx-doc/sphinx/blob/v8.2.3/sphinx/themes/basic/static/searchtools.js#L15) is a neat little interface! It's kinda unusable for me, though, because it doesn't give me access to the user's search query.

**Describe the solution you'd like**

The user's query should be provided as an argument to `Scorer.score()`.

Current:

```
    score: result => {
      const [docname, title, anchor, descr, score, filename, kind] = result;
      return score;
    },
```

Proposed:

```
    score: (query, result) => {
      const [docname, title, anchor, descr, score, filename, kind] = result;
      if (docname.includes(query)) score += 5;  // An example use case.
      return score;
    },
```

As the proposal demonstrates, one use case is to boost a score if the query is found in the URL path (using `docname` as a proxy for URL path). E.g. the docs that live under https://pigweed.dev/pw_containers/
should be top results when someone searches for `container`.

**Describe alternatives you've considered**

* If `searchtools.js` stores the query in a well-known location in `localStorage` that my custom `Scorer.score()` implementation can access, that would also work fine (and is in fact my current workaround). The `localStorage` route may be a more desirable solution because it does not require any interface modifications. It seems like a lot of `Scorer.score()` implementations could benefit from access to the query, though, so I think the interface modification is warranted.

* I don't really need access to the [parsed query terms](https://github.com/sphinx-doc/sphinx/blob/v8.2.3/sphinx/themes/basic/static/searchtools.js#L279). If anyone needs that, it seems like they could just re-invoke `_parseQuery()` from within their `Scorer.score()` method. I guess that would be expensive, because the custom scorer is invoked for each search result.

* Storing the query on the `Search` object also seems like it would work fine. `Search.query` is already taken (it's a function), so we can't use that. `Search.q` makes sense to me because it matches the URL parameter key name.

* It may also be possible to just rely directly on the `q` URL parameter. I'm not sure if it will always exist when I need it, though. For example in my [search-as-you-type](https://github.com/orgs/sphinx-doc/discussions/13222) hack I'm not sure if I can keep changing the `q` param while the user types.
