I agree that authors should have more flexibility in controlling where a `toctree` is attached within the TOC hierarchy.

For a local option, if the value is absolute, I think `:target-level:` would make that behavior clearer than `:level:`.

However, I would prefer a relative `:level-up:` value specifying how many section levels to ascend. This seems easier for authors because it relies only on the local section context rather than requiring knowledge of the full TOC hierarchy.

```rst
My title
========

My header
---------

.. toctree::
   :level-up: 1

   page1
```

Currently, the referenced document is nested beneath `My header`:

```text
My title
└── My header
    └── Page 1 title
```

With `:level-up: 1`, the two entries would instead be siblings:

```text
My title
├── My header
└── Page 1 title
```

The proposed stateful `toc-level-up` directive would be a desirable addition for documents containing several `toctree` directives. It could follow the pattern of [`highlight`](https://www.sphinx-doc.org/en/master/usage/restructuredtext/directives.html#directive-highlight), affecting subsequent `toctree` directives in the same document.

A stateful form and a local option could coexist, as `:level-up:` on an individual `toctree` would override `toc-level-up`.

Some semantics would need to be specified before implementation, for example:

* The level change should be measured from the section containing each `toctree`, not from the section containing the `toc-level-up` directive.
* Promotion beyond the available ancestors should produce a warning rather than silently clamp the level.
* The resulting hierarchy and ordering should be identical for HTML, singlehtml, LaTeX/PDF, and other builders, including hidden toctrees.
