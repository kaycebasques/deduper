After looking a bit more into the issue, I'm wondering if a solution based on [ast.literal_eval()](https://docs.python.org/2/library/ast.html#ast.literal_eval) would be acceptable?

In particular, I'm playing with the idea of replacing the [`value.split(',')`](https://github.com/sphinx-doc/sphinx/blob/1.4.6/sphinx/config.py#L364) inside `Config.convert_overrides()`, which in turn would allow the user to pass Python-like constructs to the command line  for settings that expect list of tuples (or other relatively complex types):

``` bash
$ sphinx-build -D somesetting='[("a", "b"), ("e", "f")]' ...
```

This would have also the nice side effects of:
- allowing the passing of lists that have items containing commas (`['a setting, with comma', 'another setting']`), which I _believe_ are currently not properly handled by `split(',')`.
- allow overriding settings with a slightly complex structure such as the [authors for man_page](http://www.sphinx-doc.org/en/stable/config.html#confval-man_pages), which can be a _list within a tuple within a list_ - it might be quite an edge case, but there might be other settings that can contain _lists of lists_, etc. 

As for the drawbacks, I'm concerned about the potential of breaking the current list-passing syntax (and existing setups that rely on it!), but I _believe_ (ie. still need to look in detail and for edge cases) this can be overcome by falling back to the `split(',')` method if the `literal_eval()` call fails, as the latter would fail on unquoted strings. I'm also unsure if allowing the user to pass Python constructs via command line would be considered acceptable, even if `literal_eval()` seems pretty restrictive.

In short: would this be an approach worth exploring? If so,  I'd be happy to start a pull request, try to provide an initial basic version along with tests, and look into the finer details - please be aware that this is basically a result of my first, and very basic, glance at sphinx internals.
