> Is there prior art in eg `pospell` for the type of flag to use?

I didn't find any traces of prior art for our use case.

> Is it better to use a general 'disable checking' flag, or a specific 'provenance: code block' flag?

I think 'provenance: code block' is better, as it allows different tooling to define custom behaviours, instead of using only on-off switch.

> Would the programming language of the code block be relevant?

I think it would be, maybe as a second flag 🤔 ? I imagine that some advanced tooling could check
* code snippets correctness after translation and/or parity with the source snippet,
* spelling errors in comments and string literals.

> what type of flag we should be outputting (workflow or sticky)

We should output a sticky flag (tied to a source string, not to be removed e.g. after improving the translation, like `fuzzy` flag).

> A sketch example of output you'd hope to see would be useful.

After reading the new syntax announcement again, it looks like until 2027-01-01 writing a PO entry doesn't change (doesn't use `#=` line start). Also existing `*-format` flags provide flag category as postfix, we could try to be consistent with them.
Therefore I'd hope for something similar to the following:

```pot
#: ../../tutorial/introduction.rst:32
#, code-block-provenance, python-language
msgid "# this is the first comment\n"
"spam = 1  # and this is the second comment\n"
"          # ... and now a third!\n"
"text = \"# This is not a comment because it's inside quotes.\""
msgstr ""
```
