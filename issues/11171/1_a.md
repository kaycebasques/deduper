**Is your feature request related to a problem? Please describe.**

When multiple classes share the same name in a codebase, using a reference with just the class name is ambiguous. This results in a warning such as (using a concrete example from matplotlib):

```
WARNING: more than one target found for cross-reference 'Axes': matplotlib.axes.Axes, matplotlib.axes._axes.Axes, mpl_toolkits.axisartist.axislines.Axes, mpl_toolkits.axes_grid1.mpl_axes.Axes
```

This is expected and reasonable default behavior, but it would be nice if there was a way to explicitly disambiguate these cases such that a shorter reference could be used.

This is especially relevant when it comes to inline type hints which get turned into references.
In cases of docstrings or rst files it is relatively easy to provide the longer unambiguous reference with minimal cost, including only including the last dot-separated portion in the rendered html (etc).
However, when it comes to python code/type hints, often the class if it is used often in the file it is already imported directly (e.g. `from matplotlib.axes import Axes`) and so mixing using `Axes` in code and `axes.Axes` incurs not only potentially an extra import, but also confusion because the same class is referred to in two different ways. (and using only `axes.Axes` in code is less elegant itself)

**Describe the solution you'd like**

I would like a hook, much like the one provided for missing references, but instead for when more than one target is available.
This would allow an extension to notice this warning, provide context and select the appropriate version, and avoid the warning (which results in failure with `-W`, which is desired for warnings which are not explicitly ignored)

**Describe alternatives you've considered**

Adding a configuration for an explicit mapping between a reference text and desired target:

```
explicit_reference_map = {"Axes": "matplotlib.axes.Axes"}
```

Which would intercept the reference (potentially before it even looks for potential targets) and allows the config to be explicit while the references elsewhere to be more flowing.

In this particular instance (for matplotlib's codebase, at least) it actually does select the one I want by default, and so simply being able to have a targeted warning suppression would be good enough.
As far as I can tell, I could suppress _all_ warnings from reference resolution, but not be more specific about this particular warning (with this particular target lookup).
The "more than one target" error does not get silenced by adding `("py:class", "Axes")` to `nitpicky_ignore`, which would be another route: adding something similar for all warnings to suppress via e.g. a regex.

Further alternative would be to, in the case of type hints in particular, use the context of the file to determine the namespace for the reference.

**Additional context**

This warning has been a minor issue in the past (mostly solved by lengthening the target in rst/docstring) for Matplotlib, but is more problematic as part of matplotlib/matplotlib#24976

In the short term, I'm leaning towards doing the slightly inelegant solution of using `axes.Axes` for type hints even as `Axes` is good enough for the type checker.
