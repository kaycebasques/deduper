### Describe the bug

I'm working to update [sphinx-js](https://github.com/mozilla/sphinx-js/) to run on python 3.10, and as part of that I need to update the version of sphinx it uses. I've been hitting an issue, with newer versions of sphinx detailed here https://github.com/mozilla/sphinx-js/issues/209, where type information that is currently output as `*{type}*` is being treated like a function and rendered instead as `"{type}()"`. I've bisected sphinx and tracked down the problematic change to https://github.com/sphinx-doc/sphinx/commit/4534d2d1a5755c8cbc9ef4327eab7e34a85a7de8, which was shipped as part of [sphinx-doc PR 9155](https://github.com/sphinx-doc/sphinx/pull/9155), which resolved [Sphinx-doc issue 8945](https://github.com/sphinx-doc/sphinx/issues/8945#issuecomment-812981784). Within that commit, I can revert just the changes to [docfields.py:make_xref function](https://github.com/sphinx-doc/sphinx/commit/4534d2d1a5755c8cbc9ef4327eab7e34a85a7de8#diff-f18bf3af0871669d46455026b741254522ecd7e8a729be708603249e872d37abR66-R94) and a more updated version of sphinx works fine.

After some time in a debugger with the sphinx-js test suite, I can see that in the new (problematic) code the domain ('js') provides the role ('func'), which seems to be why the xrefs are being rendered out as functions with parens appended to them. The old path is still present for specific conditions that will never occur because the inliner object is always provided.

I'm at a loss for how to move forward from within the sphinx-js code, here. I understand that library is outside the purview of this project, but I'm hoping someone can revisit the original PR and at least help me determine if this is an issue in sphinx or if it must somehow be dealt with in sphinx-js. The specific portion of the code causing me trouble has most of the review comments and a note from the reviewer stating that this new code path depends on a portion of the code base that is "ugly and hard to understand".
