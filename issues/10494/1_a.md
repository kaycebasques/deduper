### Problem I am trying to solve
I am using [sphinxcontrib-confluencebuilder](https://sphinxcontrib-confluencebuilder.readthedocs.io/en/stable/) by  @jdknight  to create multiple document sets A, B and C and want to implement intersphinx linking between them.
Set C can have references to both A and B.
The Confluence builder at `sphinxcontrib-confluencebuilder` creates inventories with links of the form
```
<base_confluence_url>/pages/viewpage.action?pageId=<page_id>
```

Since all sets A, B and C are created on the same Confluence instance (server), `<base_confluence_url>` is always the same for all packages.

The following adds to the problem a bit but is not the root cause where I am stumbling:

1. `sphinxcontrib-confluencebuilder` at the moment creates rather basic inventories that limit support to domain "std"
2. `sphinxcontrib-confluencebuilder` does not store the inventory file in the server, hence I am storing it locally after building each package

So, if I want to build documentation set C after I have build A and B and stored their inventories locally, I use a mapping like 

```
intersphinx_mapping = {
    'python': ('https://docs.python.org/3', None),
    'set_A': (<base_confluence_url>, ('_inventory/set_A/objects.inv', None)),
    'set_B': (<base_confluence_url>, ('_inventory/set_B/objects.inv', None)),
    }
```

However I found out that only references to set_B can be resolved this way, references to set_A can not be resolved.
After debug listing the content of InventoryAdapter(env).main_inventory, I found out that the content of the inventory for set_A, while being reported as read successfully, was not present at all.

### What seems to cause this behavior

After inspecting how the intersphinx extension reads and consolidates inventories, I believe that the reason is simply the fact that my `intersphinx_mapping`  is using multiple entries with distinct identifiers but with the same `target` base URI `<base_confluence_url>` and that the current implementation uses only the `target` base URI as the key of the inventory cache. As I explained, having the same `target` base URI is normal in the context of a Confluence build.

Hence, after reading an inventory from '_inventory/set_A/objects.inv' and storing it as 
```
cache['<base_confluence_url>']
```

reading of the next inventory from '_inventory/set_B/objects.inv' will **overwrite**  
```
cache['<base_confluence_url>']
``` 

and **thus eliminate all entries for set_A**. :-(

### What I think could be improved

If my assumption about the cause is correct, then I suggest to modify the caching and use either the identifier (which should be unique) or the combination of identifier and  `target` base URI as the cache identifier to ensure each inventory is treated as distinct and inventories do not overwrite each other unintentionally.
