@jayaddison, here are my thoughts on the future design:

I think the overall direction makes sense: `singlehtml` should produce globally unique, document-namespaced target IDs and generate references to those IDs directly.

I'm not sure using a literal `#` inside the ID and `%23` in the `href` is the best syntax. Browsers can handle that encoding, but it adds complexity for URL tooling, CSS selectors, JavaScript, validators, and inventories. I think a document-namespaced ID using an ordinary separator, `--`, would be simpler, for example:

```html
<dt id="document-glossary/term1--term-API">...</dt>
<a href="#document-glossary/term1--term-API">API</a>
```

`objects.inv` entries should also use the same target scheme in inventory URIs so that Intersphinx links resolve to the new IDs. [#10106](https://github.com/sphinx-doc/sphinx/issues/10106) already tracks incorrect inventory URIs generated by `singlehtml` and should be considered as part of that work.

One compatibility consideration, which may already be accounted for given the Sphinx 10 target, is that existing `singlehtml` output exposes bare IDs such as `term-API`. Bookmarks, external URLs, and manually authored links may therefore point to `index.html#term-API`. Replacing that ID would break those links, so the release notes should identify the changed `singlehtml` fragment-ID scheme and note that existing external deep links may require updating.

One separate note: namespaced IDs make it possible to link precisely to duplicate glossary terms, but they do not define how a `:term:` reference naming only `API` should choose among definitions in different documents. That remains a separate standard-domain reference-resolution question, and [#1399](https://github.com/sphinx-doc/sphinx/issues/1399) is likely the best tracking issue for it.
