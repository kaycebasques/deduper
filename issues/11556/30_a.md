I am also interested in this topic.
When dealing with build system such as [Bazel](https://bazel.build/) the option for a hash based caching might be useful.
I'm not sure yet how the Sphinx caching could effectively integrate into Bazel's (remote) cache.

But I've seen already a [concept](https://github.com/bazel-contrib/rules_python/pull/2938) ([Issue 2879](https://github.com/bazel-contrib/rules_python/issues/2879) and [Issue 2878](https://github.com/bazel-contrib/rules_python/issues/2878)) how to deal with this.

This is a bit wild, but when thinking about this, an invocation mode would be useful, in which Sphinx can be driven from an outside build system. In the read phase the input files are read isolated and translated to pickled docutils nodes or temporary nodes. That compares to a compiler that translates .c sources to .o objects. An outside build system could drive this and users would benefit from a well designed caching system. The next phase is the resolution that needs the Sphinx (+extensions) central entity. The write phase again could be driven from the outside for each to-be-written output file. Ideally the intermediate outputs of Sphinx (doctrees, environment) are reproducible for this to work. I know this also depends on the extensions.

For the record, Bazel uses sha256 checksums.
