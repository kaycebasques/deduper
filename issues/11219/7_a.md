> Do you think the fact that nodes added using the Sphinx.add_node method are deconflicted by class name (only) should be documented? It's not mentioned in the [existing docs](https://www.sphinx-doc.org/en/master/extdev/appapi.html#sphinx.application.Sphinx.add_node).

No really because it can be inferred (although not necessarily directly). It says "Obviously, translators for which you don’t specify visitor methods will choke on the node when encountered in a document to translate", so we need to know how translator define visitor methods. If you want add a node, then you should ensure that this node can be properly handled by translators or at least, you need to know how translators handle nodes. Since they are node visitors implementing the visitor pattern, you should then know that visitor pattern (as implemented in `docutils`) uses the class name only.

The public API exposed by `add_node` should be assuming that you are providing the visitor methods yourself (like in their example). If you don't, then it's assuming you know what you are doing. 

Still, I think the developer docs should be updated in general. I personally never relied on it and only looked at the Sphinx and docutils source code directly (that's how I generally code whatever the project is: looking at the original API).

There is no real documentation on how to test when you contribute. I digged myself into the testroots and the `sphinx.testing` plugin to understand what happens but perhaps we should write something for contributors. 

> Secondly, do you think it's a deficiency of the test framework that classes of errors like this one cannot be tested

Concerning this point in particular, I think it depends on the dev. Personally, asserting outputs should be done programatically using `capsys`, `status` or `warning`. It's always better to ensure that something didn't happen by checking using an assertion, instead of relying on "if this something happens, then an exception is raised". Again, I think a contributor's guide for writing tests should be written.
