@picnixz I read your previous posts but I haven't had the time to get back to this. My next step would be going through the standard library Enum types and writing up an example for each dataype (including `enum.IntEnum`, `enum.Flag`, etc...) to make sure there's no special case "surprise". But the general approach is as follows:

The most demanding use case for `Enum` is having several hundred members per class, in such cases I've found there's one single optimal solution (packing all the attributes into a google-style docstring just isn't going to render well). It looks like this:

```rst
.. autoclass:: MyEnumClass
    :no-members:

     .. dropdown:: Show members

          .. autoattribute:: EnumMember1

              .. to get a custom presentation value with the `.. autoattribute::` directive 
                  the `:annotation:` option should be used.

              - Complicated prose
              - Cross-reference to bibliography

              .. admonition:: Example
                  Because the end-user will really need it.

           .. attribute:: EnumMember2
               :type: A_type_with_a_reference_that_does_not_render_correctly_using_autodoc
               :value: "a value that's written by hand, there's no automatic value extraction with the domain directive."

               This is the alternative if value or type need to be written explicitly due to any bugs (for example #9813).
    
           .. over a hundred of these attributes per Enum class (and you have lots of these Enum classes).
```

Some notes:

- Notice the use of [`.. dropdown::`](https://sphinx-design.readthedocs.io/en/latest/dropdowns.html) which comes bundled with recent themes like [PyData theme](https://pydata-sphinx-theme.readthedocs.io/en/stable/index.html) or [sphinx-book-theme](https://sphinx-book-theme.readthedocs.io/en/stable/). It's aim is to pack all the Enum members into a single collapsed DDL so they don't clutter the API.
- This method avoids cluttering the docstring with a long attribute list that's also limited in line length by style checkers, because each individual attribute might need a lengthy elaboration. It focuses on only extracting the class docstring and keeping any additional complexity in the `.rst` file.

----

- **Counter-Example 1:**

> but if we don't want expose the _My123 enumeration class, we would have _My123 being exposed visually because of the constructor dataclass but we would have value = 1

Pythonic use here would be [`member.value`](https://docs.python.org/3/library/enum.html#enum.Enum.value): 

```py
@dataclass
class Public:
    value = _My123.not_a_two_nor_a_three.value
```

If you want to associate a name to a value (definition of an Enum member) and expose that name to the end-user then the name should be public. If you only want the value then visibility of the name doesn't matter.

- **Several hypothesis**:

> We could also indicate how it should be documented at the level of the directive, though it would likely be useless since people rarely write autoattribute themselves.

As I started by demonstrating any Enum of reasonable length and complexity will require documenting the attributes individually. I agree there's not much sense putting an option under the individual class directive on how the Enum should be rendered elsewhere - or having an option under each directive where an Enum might be used.

> Add a global flag to use enumeration values instead.

This might satisfy users looking to generate mostly automated documentation with little or no custom reStructuredText involved. But fundamentally the problem at hand is a `dataclass` specific bug.

> Add a configuration value containing a list of enumeration class names for which the value should be used instead.

I think the pythonic way of looking at this is getting the qualified name when a user writes `Enum.member` and getting the value when you write `Enum.member.value`. Looking carefully at the OP that's what's being asked for! It seems to me this last hypothesis is a kind of additional [`autodoc_type_aliases`](https://www.sphinx-doc.org/en/master/usage/extensions/autodoc.html#confval-autodoc_type_aliases) specific to the Enum type, but the idiomatic solution (and what users will expect) is for `Enum.member` and `Enum.member.value` to work as usual where they are used. I haven't seen any FRs asking for additional "magic" functionality with a solid use case proving an expressed need.
