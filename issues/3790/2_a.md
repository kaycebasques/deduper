Just random thoughts triggered by [this example of use of tcolorbox](https://github.com/sphinx-doc/sphinx/issues/4283#issuecomment-350980568), not for code-blocks but for admonition.

in the long term, Sphinx might adopt `tcolorbox` indeed by default for its layout (inclusive but not limited to code-blocks.) See [this comment](https://github.com/sphinx-doc/sphinx/issues/3099#issuecomment-262759760) in connection with code-blocks.

- we must support various TeX distributions, and `tcolorbox` via `tikz/pgf` is very big dependency which has changed over recent years.

- we can't reasonably add a user interface for all possible customization keys of a `tcolorbox`; as [this example](https://github.com/sphinx-doc/sphinx/issues/4283#issuecomment-350980568) illustrates, they are numerous. However we can presumably emulate currently provided interface and add a "contain all extras for tcolorbox setup" key.

- note that previous evolutions of layout have been quite conservative, and lots of efforts went into not modifying for example vertical layout except intentionally. Switch to `tcolorbox` means rather drastic change, interface is at a much higher level than for `framed.sty` and controlling exactly what goes into the main vertical list is not an option, we presumably will simply use `tcolorbox` interface and be happy with result. As do 99% of LaTeX users which do not have the knowledge actually needed of TeX's innards and add manual `\vspace{..}` to "correct"; whereas `sphinx.sty` currently is very precise into controlling line spacing even when there are tables or code-blocks or admonitions.

- a possible intermediate step would be to provide an extra style file, refactoring all LaTeX layout using `tcolorbox` but it would not be activated by default.

- definitely this will slow down compilation, but may not be so noticeable on fast hardware.
