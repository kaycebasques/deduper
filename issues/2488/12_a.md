_(My reply from our off-list discussion.)_

My one and only concern with this PR is API design.  The `sphinx.application.Sphinx()` object is part of our external contract with developers such as you, and isn't something hidden in a dark shed where we don't care about design questions.  There are three reasons I consider this change bad, or at least trending towards a bad direction:
- **Clarity**:  The application API (this one constructor method we're talking about) is already quite convoluted.  I would prefer if we found other ways to modify the object.  An example could be deferring the builder initialization into `Sphinx.build()`, so that `Sphinx()` no longer needs either — a buildername or a builderclass.
- **Consistency**:  While I agree the builder is important, I like the way it is just another extension point currently.  From an extension's view, it's no different to anything else — be it directives, parsers, or autodocumenters.  I think if we further the specialness of builders, the same argument could be made for parsers tomorrow.
- **Convenience**:  I agree that your use case is legit;  I don't think we should just follow the easiest path and tack on a bolt here and there to fix it quickly.  _«Simple things should be simple, complex things should be possible.»_<br/>
  Maybe if we made a wrapper object that allowed something like: `Sphinx(confoverrides={'extensions': [InMemoryExtension(lambda app: app.add_builder(MyCoolBuilder)]})`<br/>
  Or, if we just allowed `confoverrides=` to contain a `'setup'` key (like any other config, that's what confoverrides is for), like: `Sphinx(confoverrides={'setup': lambda app: app.add_builder(MyCoolBuilder)})`
