I recently ran into this issue myself: the basic issue that I observed is as follows:

When the documents is larger than 10 times the number of workers, there will be more batches than workers.  Consequently, after some batches have completed, new workers will be forked with the updated environment containing previously completed batches, and after they complete they will send back their pickled environment containing both the updates from the documents in the batch but also the state from the previously-completed batches.  The end result is that the total amount of work is quadratic in the number documents.  In fact even if the number of batches is equal to the number of workers, this problem can still occur to some extent, because due to the way the existing parallel task launching works, some tasks may finish and have their updates merged into the main process environment before additional tasks are forked.

There are various approaches one could take to improve things:

- Simplest is to just make the number of batches equal to the number of workers and ensure all tasks are forked before the environment is updated.  This can be accomplished with a monkey patch fairly easily.  The main downside is that logging is delayed longer and the work may end up unevenly distributed.
- An alternative would be to fork a fixed number of workers, have them all pop documents to process from a shared queue, steam back logs after each document, and send the updated environment only after all documents have been processed.  This would not introduce any extension compatibility issues since it would retain the same forking model, and would fix both the delayed logging and uneven work distribution of the simple workaround.
