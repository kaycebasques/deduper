**Is your feature request related to a problem? Please describe.**
With such kind of input:

```rst
.. code-block::
   :class: red crucial
           
   1+1
```

the HTML output will contain

```html
<div class="red crucial highlight-default notranslate"><div class="highlight"><pre><span></span><span class="mi">1</span><span class="o">+</span><span class="mi">1</span>
</pre></div>
</div>
```

in contrast the `.tex` file only provides

```latex
\begin{sphinxVerbatim}[commandchars=\\\{\}]
\PYG{l+m+mi}{1}\PYG{o}{+}\PYG{l+m+mi}{1}
\end{sphinxVerbatim}
```

i.e. the 'red' and 'crucial' classes got lost.  So the HTML gets styling possibilities via CSS for which no equivalent currently exists in PDF via LaTeX output.

**Describe the solution you'd like**
A clear and concise description of what you want to happen.

With the following diff:

```diff
diff --git a/sphinx/writers/latex.py b/sphinx/writers/latex.py
index 5debd681f..e031eaa97 100644
--- a/sphinx/writers/latex.py
+++ b/sphinx/writers/latex.py
@@ -1791,6 +1791,11 @@ class LaTeXTranslator(SphinxTranslator):
             else:
                 hlcode += r'\end{sphinxVerbatim}'
 
+            classes = node.get('classes', [])
+            for _c in classes:
+                hlcode = '\\begin{sphinxuseclass}{pre.%s}\n' % _c + hlcode
+                hlcode += '\n\\end{sphinxuseclass}'
+
             hllines = str(highlight_args.get('hl_lines', []))[1:-1]
             if hllines:
                 self.body.append(CR + r'\fvset{hllines={, %s,}}%%' % hllines)
```

the `.tex` file will look like this

```latex
\begin{sphinxuseclass}{pre.crucial}
\begin{sphinxuseclass}{pre.red}
\begin{sphinxVerbatim}[commandchars=\\\{\}]
\PYG{l+m+mi}{1}\PYG{o}{+}\PYG{l+m+mi}{1}
\end{sphinxVerbatim}
\end{sphinxuseclass}
\end{sphinxuseclass}
```

where the `sphinxuseclass` architecture available since Sphinx 4.1.0 (#9166) is put to use.

I.e. if the LaTeX environments `sphinxclasspre.crucial` or `sphinxclasspre.red` are not defined then nothing special  happens.

But these environments can be defined in LaTeX preamble in the  `conf.py`  and configured  for example to use `\sphinxsetup` to modify some styling,  say the background colour of the code-block, or the border width, or they can use some LaTeX environments such as ``adjustwidth`` from the ``changepage`` package to modify at this location the indentation and available width, or they can issue some `\fvset`  to use the `fancyvrb` options for example for the font size etc...

In the above diff, I use `pre.` prefix because when the `sphinxuseclass` is expanded it does not know it is supposed to style some code-block, so with the prefix we add this information and it becomes used because it is mapped to the environment name.

**Describe alternatives you've considered**
A clear and concise description of any alternative solutions or features you've considered.

In the case of code-blocks only, I vaguely consider using Pygments `verboptions` to pass extra options to the `sphinxVerbatim` i.e. beyond `commandchars` but this then requires extending `fancyvrb.sty` option list, and is too specialized and too LaTeX intensive, so dropped the idea before implementing it.

**Additional context**
Add any other context or screenshots about the feature request here.


I am not doing a PR yet because I was a bit too focused on code-blocks (as the origin of this feature request is partly in the discussion at #10719) and didn't really look at the other block elements which may benefit possibly from such styling.

The idea here is to allow, for one specific display element in the produced PDF to be styled differently from others of the same type.

Recently Sphinx 5.1.0 added more styling to code-blocks and to the warning-type admonitions as well as to topic directive. So the natural thing would be to let those elements become class aware too, as classes can always be added by `rst-class` directive.

Also it is perhaps better with `` for _c in reversed(classes):``  in the above so that we get
```latex
\begin{sphinxuseclass}{pre.red}
\begin{sphinxuseclass}{pre.crucial}
\begin{sphinxVerbatim}[commandchars=\\\{\}]
\PYG{l+m+mi}{1}\PYG{o}{+}\PYG{l+m+mi}{1}
\end{sphinxVerbatim}
\end{sphinxuseclass}
\end{sphinxuseclass}
```
matching  the order ``red crucial`` in the input.  But this means that ``crucial`` will make the final decisions possibly overruling ``red`` if adjusting same things.  So it is a matter of deciding how to interpret the order of space separated class names in the input.

(also, using ``reversed()``  will be coherent with the `latex.py` handling of the ``container`` directive node as already implemented, where the first listed class defines the most exterior environment and subsequent classes are nested deeper and deeper).
